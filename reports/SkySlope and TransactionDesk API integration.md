# Auto-syncing SkySlope and TransactionDesk contracts into our Hub

**Bottom line: both platforms can feed transactions into our Agent Hub with no re-keying, but neither gives us the easy "it just works" button... so we build a small sync engine ourselves and start with SkySlope.** When an agent writes or executes a contract, our app can pull in the parties (names, emails, phones, roles), the property, the key dates (offer accepted, closing, funding, possession), the status, and the signed PDFs. The catch is that both vendors gate API access behind a partner conversation (no instant self-signup), and the ideal "a contract was just executed" push notification is only reliably available on the e-signature side, not the transaction side. SkySlope should be first because we already hold SkySlope Access Keys from 2020 and its Forms API exposes everything we need in one place. TransactionDesk (Lone Wolf) is a strong second with an even richer set of key-date fields, but it has zero transaction webhooks (poll-only) and does not publish its production web address. The clean way to hold both ... plus Dotloop later ... is one internal transaction record that links out to each provider through an `external_links` table, so a signed addendum updates the existing deal instead of creating a duplicate. Several make-or-break details (do the 2020 keys still work, does SkySlope offer transaction webhooks, what is Lone Wolf's production URL, rate limits, pricing) are undocumented publicly and require a call with each vendor's API team, flagged throughout.

---

## For the non-engineer: what this means and what to do next

**The goal in plain terms.** An agent on our team does what they already do: writes up and signs a purchase agreement inside SkySlope or TransactionDesk. Without anyone retyping anything, a matching transaction appears (or updates) inside the Sold It Today Agent Hub, carrying the buyer and seller and agents as contacts, the property address, the dollar amounts, the critical dates, and the executed paperwork. That is entirely achievable with both platforms' APIs.

**Why it is not a one-click setup.** Neither SkySlope nor Lone Wolf lets a developer sign up on a website and start pulling data five minutes later. Both require filling out a request form and talking to their integrations team, who then hand over secure credentials ([lwolf.com/api-getting-started](https://www.lwolf.com/api-getting-started); [API Evangelist provider profile](https://providers.apievangelist.com/providers/skyslope/)). And there is no reliable Zapier or Make shortcut for the transaction data we care about... the off-the-shelf connectors either do not exist or only handle contacts ([Tray.ai SkySlope connectors](https://tray.ai/connectors/skyslope-box-integrations); [Zapier: zipForm Plus](https://zapier.com/apps/zipform-plus/integrations)). So this is a custom build, which is actually the right fit for us anyway because we control a Next.js + Supabase app and can build exactly the sync we want.

**The recommendation: build SkySlope first.** We already have two SkySlope Access Key IDs with paired Secrets from 2020 (per our accounts notes), and SkySlope's main API exposes transactions, parties, dates, and signed PDFs all in one place. That is the shortest path to a working demo. The very first thing to do is email or call SkySlope's partner team and ask five specific questions (listed in the developer section): whether those 2020 keys still work, whether they now offer a "new transaction" or "status changed" webhook, how to get partner credentials, what the rate limits are, and whether there is a cost. Those answers decide the exact shape of the build.

**What "done" looks like in version one.** A one-way sync (vendor into our app, never the reverse to start). When a contract is executed, the deal shows up in the Hub with everybody's contact card, the address, the accepted and closing dates, and the signed contract PDF stored privately. If an addendum or amendment gets signed later, the existing deal updates... it does not spawn a second copy.

**Honest expectation setting.** The slowest, least-controllable part is not the coding... it is getting partner approval and any signed agreement from the vendors, which can add weeks and is outside our control ([SuperGood: Dotloop API report](https://supergood.ai/docs/dotloop-api)). Start those conversations now, in parallel with the build.

## SkySlope: the Forms API carries everything, but access and webhooks need a vendor call

**Access is partner-gated, not self-serve.** SkySlope publishes a live reference for its Partnership/Forms API at [forms.skyslope.com/partner/api/docs](https://forms.skyslope.com/partner/api/docs), but there is no public signup page to request API partnership... you work with SkySlope's Customer Success / onboarding team, who issue a partner `Client ID` and `Client Secret` inside a **password-protected zip with the password sent separately** to the primary technical contact ([Drivetrain SkySlope integration guide](https://integrations.drivetrain.ai/integration-guide/readme/others/integrating-with-skyslope); [API Evangelist provider profile](https://providers.apievangelist.com/providers/skyslope/)). There are three API programs: the **Partnership/Forms API** (`https://forms.skyslope.com/partner/api`), the **Offers API** (`https://offers.skyslope.com/offers-api`), and a **Transaction Management API in BETA** (`https://api.skyslope.com/api`) ([API Evangelist repo README](https://github.com/api-evangelist/skyslope)). The Forms API is the one to target: it exposes files, contacts, documents, and signed PDFs in a single place, whereas the conceptually-cleaner Transaction Management API is BETA with no public endpoint reference ([API Evangelist repo README](https://github.com/api-evangelist/skyslope)).

**Two auth schemes, and our 2020 keys are the legacy kind.** The modern Forms API uses **OAuth 2.0 authorization-code flow with PKCE** (`code_challenge_method=S256`), authorizing at `https://accounts.skyslope.com/oauth2/authorize` and exchanging at `https://accounts.skyslope.com/oauth2/token`; you must request the `offline_access` scope to receive a refresh token, and **refresh tokens rotate on every use** ([SkySlope Partner API docs](https://forms.skyslope.com/partner/api/docs)). The Offers API instead uses client-credentials with HTTP Basic auth against `POST /ext/token` ([SkySlope Offers Auth OpenAPI mirror](https://raw.githubusercontent.com/api-evangelist/skyslope/refs/heads/main/openapi/skyslope-auth-api-openapi.yml)). The **Access Key + Secret** scheme ... the kind we hold from 2020 ... is a per-user credential generated in the SkySlope UI under My Account > Integrations > Generate New Key, where the secret is shown only once ([Drivetrain guide](https://integrations.drivetrain.ai/integration-guide/readme/others/integrating-with-skyslope); [API Nation KB](https://support.apination.com/kb/article/62-how-to-locate-your-skyslope-access-secret-keys/)). Those keys carry the same privileges as the user who created them, so an **agent key sees only that agent's files and a broker/admin key is needed for the whole brokerage** ([Drivetrain guide](https://integrations.drivetrain.ai/integration-guide/readme/others/integrating-with-skyslope); [Sisu KB](https://kb.sisu.co/en/articles/3498325-integrating-sisu-and-skyslope)). **Flag for a vendor call: whether our 2020 Access Keys still work and against which API is undocumented anywhere... they may have been migrated to the OAuth model or may still hit a legacy endpoint, and no HMAC request-signing scheme is documented for any SkySlope API** ([skyslope note gaps](https://forms.skyslope.com/partner/api/docs)). What we would store in env vars depends on the path: for Forms, `SKYSLOPE_CLIENT_ID`, `SKYSLOPE_CLIENT_SECRET`, `SKYSLOPE_REDIRECT_URI`, plus the per-user rotating refresh token kept in a secure store; for the legacy path, `SKYSLOPE_ACCESS_KEY` + `SKYSLOPE_SECRET_KEY`.

**The data we need is all there.** The File (transaction) object carries `id`, `name`, `fileType`, `representationType` (Buyer/Seller/Tenant/Landlord), `mlsNumber`, `purchasePrice`, `closingDateTime`, `acceptanceDateTime`, `property`, `contacts`, `commissions`, `documentData`, and audit fields, read via `GET /files` (paginated, filterable, sortable) and `GET /files/{fileId}` ([SkySlope Partner API docs](https://forms.skyslope.com/partner/api/docs)). The Contact (party) object carries `id`, `type` (Buyer, Seller, BuyerAgent, TitleOfficer, and so on), name fields, `email`, phone numbers, `companyName`, license/MLS codes, and `primaryAddress`, read via `GET /files/{fileId}/contacts` ([SkySlope Partner API docs](https://forms.skyslope.com/partner/api/docs)). Signed and executed PDFs are listed and downloaded via `GET /documents/signed/{fileId}` and `GET /documents/signed/{fileId}/envelope/{formsEnvelopeId}`, each with `envelopeId`, `digisignDocumentGuid`, `dateSigned`, `documentName`, `documentUrl`, and `documentAvailable` ([SkySlope Partner API docs](https://forms.skyslope.com/partner/api/docs)). **Flag: there is no documented top-level pipeline "status/stage" field on the Forms File, and contingency/inspection/financing deadlines are not exposed as discrete File dates... they likely live inside parsed form fields (`documentData`/`fields`) or in the BETA Transaction Management API** ([SkySlope Partner API docs](https://forms.skyslope.com/partner/api/docs)).

**Webhooks are thin: one documented push event, otherwise poll.** The only publicly documented webhook is the signed-documents webhook, subscribed via `POST /documents/sign/subscribe/{fileId}` (scope `forms.webhooks`, body a `webhookUrl` string, sample response `{"subscribed": true}`), and even its payload format is not published ([SkySlope Partner API docs](https://forms.skyslope.com/partner/api/docs)). No "transaction created" or "status changed" webhook is documented, so new files and field changes must be caught by polling `GET /files` ([SkySlope Partner API docs](https://forms.skyslope.com/partner/api/docs)). **Flag: the full webhook event catalog is undocumented and must be confirmed with SkySlope** ... if they offer file-created or status-changed webhooks, the design simplifies considerably. On rate limits, SkySlope publishes no numeric figure; throttling returns HTTP 429 and clients should back off and honor `Retry-After`, but this guidance comes from an unofficial API Evangelist profile **not verified against a SkySlope page** ([API Evangelist rate-limits profile](https://apis.io/rate-limits/skyslope/skyslope-rate-limits/)). No public API pricing exists; it is negotiated per partner agreement ([API Evangelist rate-limits profile](https://apis.io/rate-limits/skyslope/skyslope-rate-limits/)). And there is **no reliable Zapier or Make connector**... the Zapier SkySlope app path returns 404 and Tray.ai states plainly there is no pre-built SkySlope connector ([Zapier 404](https://zapier.com/apps/skyslope/integrations); [Tray.ai](https://tray.ai/connectors/skyslope-box-integrations)). Third parties like API Nation and LeadsBridge wrap SkySlope using the user's Access Key + Secret or username/password, not a native connector ([API Nation KB](https://support.apination.com/kb/article/62-how-to-locate-your-skyslope-access-secret-keys/); [LeadsBridge](https://leadsbridge.com/integrations/skyslope/outgoing-webhook)).

**Product lines that matter.** SkySlope is several separate products, not one API. **SkySlope Forms** (the Partnership API) carries the transaction, party, and document data; **DigiSign** is the e-signature engine embedded inside Forms (signed documents reference `digisignDocumentGuid`), so we get e-sign data free through the Forms envelope/signed-document endpoints with no separate DigiSign integration ([SkySlope Partner API docs](https://forms.skyslope.com/partner/api/docs); [Rechat SkySlope note](https://help.rechat.com/whats-new/skyslope-integration-fill-send-and-sync-without-leaving-your-deal)). **Offers** is a separate API for listings and offers, and **SkySlope Books** (accounting/commission disbursement) has no public API found ([API Evangelist provider profile](https://providers.apievangelist.com/providers/skyslope/); [GetApp SkySlope profile](https://www.getapp.com/all-software/a/skyslope)). For our use case, target Forms and ignore the rest.

## TransactionDesk / Lone Wolf: richer dates, a real e-sign webhook, but no transaction webhooks and a hidden production URL

**A formal, recently centralized portal... still gated.** Lone Wolf runs official docs at [apidocs.lwolf.com](https://apidocs.lwolf.com/) and **launched a centralized API Portal in February 2026** to accelerate integrations across its "Foundation" cloud ([Lone Wolf press release](https://www.lwolf.com/press-releases/lone-wolf-launches-api-portal-to-power-real-estate-connectivity); [HousingWire](https://www.housingwire.com/articles/lone-wolf-launches-integration-hub-to-connect-real-estate-brokerage-tech-and-eliminate-data-silos/)). Access is request-gated: you "complete the access request form" and "a member of our integrations team will be in touch" ([lwolf.com/api-getting-started](https://www.lwolf.com/api-getting-started); [lwolf.com/api-portal](https://lwolf.com/api-portal)), with an integration-help line at 1-888-349-0628. The portal lists **10 REST APIs**, and for transactions + parties + documents the right one is the **TransactionDesk Partner API v2.0** ([apidocs.lwolf.com](https://apidocs.lwolf.com/); [TransactionDesk doc](https://apidocs.lwolf.com/doc/transactiondesk-api)). Be aware there are several transaction-ish APIs (TransactionDesk, a **Deals API** using JWT login, and a **Transact API**) that the portal does not disambiguate... worth asking Lone Wolf which is the current recommended surface ([apidocs.lwolf.com](https://apidocs.lwolf.com/)).

**OAuth, with an enterprise flow built for server-side sync.** TransactionDesk uses OAuth 2.0 with two flows. The **Authorization Code flow** redirects the user to `https://api.pre.transactiondesk.com/oauth/authorize` and exchanges a one-time code (**expires in 10 minutes**) at `POST /oauth/token`, then sends `Authorization: Bearer <token>` on every request ([transactiondesk-api doc](https://apidocs.lwolf.com/doc/transactiondesk-api)). The **Client Credentials flow** (better for a server-side CRM sync with no per-user browser consent) uses `grant_type=client_credentials` with no redirect and an **`On-Behalf-Of` header carrying the target user's GUID** ([transactiondesk-api doc](https://apidocs.lwolf.com/doc/transactiondesk-api)). Env vars to plan for: `LWOLF_CLIENT_ID`, `LWOLF_CLIENT_SECRET`, the token host, and a stored mapping of `On-Behalf-Of` GUIDs per agent whose transactions we read; the `client_id=Lonewolf` seen in the doc example is a placeholder, and we receive our own ([transactiondesk-api doc](https://apidocs.lwolf.com/doc/transactiondesk-api)). **Flag: Bearer token lifetime and refresh mechanics beyond the 10-minute code expiry are not shown and must be confirmed.**

**The strongest key-date coverage of any vendor here.** The API reads transactions, contacts/parties by role, documents, form libraries, users, and statuses, all under the `/v2/` namespace ([transactiondesk-api.yaml](https://apidocs.lwolf.com/doc/transactiondesk-api.yaml)). Property fields include street, city, county, state, zip, subdivision, year built, school district, and legal description; listing fields include `mlsNumber`, `listPrice`, `expirationDate`; and purchase/key dates include `purchasePrice`, `offerDate`, `offerExpirationDate`, `offerAcceptanceDate`, `applicationDate`, `approvalDate`, `depositAmount`, `fundingDate`, `possessionDate`, and `closingDate` ([transactiondesk-api doc](https://apidocs.lwolf.com/doc/transactiondesk-api)). Parties come from `GET /v2/transactions/{id}/contacts` with roles from `/v2/transactions/contacts/types`, and status from `/v2/transactions/statuses` ... so unlike SkySlope's Forms API, TransactionDesk gives us explicit status and a far fuller date set ([transactiondesk-api.yaml](https://apidocs.lwolf.com/doc/transactiondesk-api.yaml)). There are also SSO "view-url" endpoints that return deep links back into TransactionDesk ([transactiondesk-api.yaml](https://apidocs.lwolf.com/doc/transactiondesk-api.yaml)). Documents are retrieved via `GET /v2/transactions/{id}/documents/{documentId}`, which returns the file as a **Base64-encoded string in a `binary` field** ([transactiondesk-api.yaml](https://apidocs.lwolf.com/doc/transactiondesk-api.yaml)).

**Two large flags on reads.** First, **only the preproduction host `api.pre.transactiondesk.com` is published... the production base URL is not public anywhere** (it is probably `api.transactiondesk.com`, but do not assume) ([transactiondesk-api.yaml](https://apidocs.lwolf.com/doc/transactiondesk-api.yaml)). Second, whether an e-signed document automatically lands in the transaction's `/documents` list is unverified... we may have to hit the e-sign API too, and the pagination/filtering/"modified since" query params on `GET /v2/transactions` (critical for cheap polling) are not confirmed ([transactiondesk-api.yaml](https://apidocs.lwolf.com/doc/transactiondesk-api.yaml)).

**No transaction webhooks... the event hook lives on e-signature.** Reading the OpenAPI spec directly confirms **zero webhook, callback, event, or subscription endpoints on the TransactionDesk API... it is poll-only** ([transactiondesk-api.yaml](https://apidocs.lwolf.com/doc/transactiondesk-api.yaml)). The only real event hook in the whole Lone Wolf ecosystem is on the e-signature side. Lone Wolf's e-sign, formerly **Authentisign**, is now **eSignature** alongside a new API-first product, **Inkless**, built on the Authentisign engine with "full signing, templating, and webhook capabilities from day one" and an instant free sandbox at signinkless.com ([Lone Wolf Inkless press release](https://lwolf.com/press-releases/lone-wolf-launches-inkless-disrupting-legacy-e-signature-market-with-transparency-and-api-first-approach); [signinkless.com](https://signinkless.com/)). The **Inkless Signing Status Webhook** POSTs a JSON payload (`signingId`, `statusId`, `status`, `eventDate`, and crucially `transactionId`) whenever status changes, with status values 0 Draft, 1 Sent, 2 Signed, **3 Completed**, 4 Rejected, 5 Reset, 6 Expired ([Inkless documentation](https://signinkless.com/documentation/)). That `transactionId` is the natural join key back to a TransactionDesk transaction, though **whether it is the same identifier as the TransactionDesk `{id}` must be verified** ([Inkless documentation](https://signinkless.com/documentation/)). Inkless auth is a separate credential set: a JWT Bearer token from the dashboard plus an `externalId` header (`INKLESS_JWT` / `INKLESS_EXTERNAL_ID`) ([Inkless documentation](https://signinkless.com/documentation/)).

**Costs, limits, and no-code all undocumented or weak.** Rate limits, data-retention windows, compliance posture (SOC 2, data residency), and pricing are **not published for TransactionDesk/Deals/Back Office and require a direct Lone Wolf conversation** ([transactiondesk-api doc](https://apidocs.lwolf.com/doc/transactiondesk-api); [HousingWire](https://www.housingwire.com/articles/lone-wolf-launches-integration-hub-to-connect-real-estate-brokerage-tech-and-eliminate-data-silos/)). The only piece we can trial today without a partner deal is the Inkless sandbox ("No credit card required") ([Inkless sandbox signup](https://signinkless.com/get-your-sandbox-access/)). On no-code, only a **minimal zipForm Plus Zapier app** exists ... one trigger (New Contact), one action (Create Contact), contacts-only, with no TransactionDesk or eSignature coverage ([Zapier: zipForm Plus](https://zapier.com/apps/zipform-plus/integrations)). The transactions/documents expansion promised back in 2014 never shipped publicly ([Inman, 2014](https://www.inman.com/2014/11/26/zipform-plus-users-can-pull-contacts-from-100s-of-web-apps/)). **Zapier/Make is not a viable path for TransactionDesk transaction data.**

**Product-line note.** zipForm/zipTMS is the separate, California-centric forms+transaction product with a weak public automation story; the ZipForm API is "licensed to partners"; MoxiWorks, Cloud CMA, and LionDesk did not surface as separate API entries and should be treated as out of scope until confirmed ([apidocs.lwolf.com](https://apidocs.lwolf.com/)). For us, TransactionDesk Partner API v2.0 paired with the Inkless webhook is the surface.

## The recommended build: one-way sync, webhook-plus-reconciler, vendor-independent links

**The pattern, in one sentence: treat every vendor event as "something changed, go pull it," and make every write idempotent against a stable external ID.** This single idea makes the webhook path and the polling path converge on the same "fetch + upsert" code, which is exactly how Dotloop advises you build against it (a single action fires several events, so you re-fetch the resource rather than trusting the event body) ([Dotloop Public API v2 docs](https://dotloop.github.io/public-api/)).

**(a) The one-way sync flow (vendor into our app).** The proven receiver shape, drawn from Dotloop's documented contract and general webhook best practice, is: verify the signature against the raw bytes before parsing, persist the raw payload immediately, return 2xx fast, then process asynchronously and idempotently ([DEV: Webhook best practices](https://dev.to/henry_hang/webhook-best-practices-retry-logic-idempotency-and-error-handling-27i3); [Dotloop Public API v2 docs](https://dotloop.github.io/public-api/)). Concretely for Next.js + Supabase:

1. **Webhook receiver** ... a Next.js Route Handler on Vercel (or a Supabase Edge Function) that reads the raw body, verifies the signature, INSERTs the event into a `webhook_events` table with a **unique index on `(provider, external_event_id)`** so a duplicate insert fails cheaply and becomes the idempotency gate, then returns 2xx immediately. Do no heavy work here, because webhook senders give tight response budgets (Dotloop allows only **5 seconds** before it retries) and serverless cold starts can blow that ([Dotloop Public API v2 docs](https://dotloop.github.io/public-api/)). SkySlope's signing webhook and the Inkless `status 3 Completed` webhook both land here.
2. **Async worker** ... a separate process (Supabase Queue consumer on the pgmq extension, or a cron-driven function) reads the event row and does the real work: call the vendor to pull the current transaction + contacts + documents, map fields, and upsert ([Supabase Queues](https://supabase.com/docs/guides/queues); [Supabase Edge Functions](https://supabase.com/docs/guides/functions)). Note pgmq gives consumer-redelivery exactly-once within a visibility window, **not** enqueue dedup... dedup is enforced by your own unique index ([Supabase Queues](https://supabase.com/docs/guides/queues)).
3. **Scheduled polling reconciler** ... because webhook delivery is at-least-once and lossy and retry windows vary wildly by provider, a reconciler is mandatory, not optional ([Webhookrelay: retries & idempotency](https://webhookrelay.com/blog/webhook-retries-and-idempotency/)). Drive it with Vercel Cron or Supabase pg_cron. Store a per-account cursor (`updated_at` timestamp or ID) and resume from it; a failed run resumes from the same cursor rather than restarting ([Airbyte: incremental syncs](https://docs.airbyte.com/connector-development/connector-builder-ui/incremental-sync); [Nango: sync efficiency](https://www.nango.dev/docs/guides/functions/syncs/sync-efficiency)). The known pitfall: a last-modified filter misses records created once and never touched again, so pair it with a creation-time filter or ID cursor and run a periodic full reconcile (nightly) ([Flxpoint: syncing incrementally](https://www.apihelpcenter.flxpoint.com/docs/guides/syncing-data-incrementally)). For SkySlope the reconciler polls `GET /files`; for TransactionDesk it polls `GET /v2/transactions`. For both, this is the primary ingestion mechanism for new transactions and status changes, with webhooks only catching the "executed" moment.
4. **Document ingestion** ... when a document event fires, the worker pulls the signed PDF (SkySlope `GET /documents/signed/{fileId}`; TransactionDesk decode the Base64 `binary`) and streams it into a **private Supabase Storage bucket** at a deterministic key like `org/{org_id}/transaction/{txn_id}/{provider}/{external_doc_id}-{version}.pdf`, inserting a `documents` row keyed by checksum or `external_doc_id + version` so re-pulls upsert rather than duplicate; serve to the app via short-lived signed URLs ([Supabase: integrating with Storage](https://supabase.com/docs/guides/functions/storage-caching)). A strong **vendor-agnostic fallback** that matches our existing "unique inbound email per transaction" plan: mint a per-transaction inbound address, route it through Postmark/SendGrid/Mailgun inbound parsing, and run attachments through the same Storage path ... this captures PDFs that only ever arrive by email and covers any vendor whose document API is gated ([Postmark: parse an email](https://postmarkapp.com/developer/user-guide/inbound/parse-an-email); [DEV: email to S3](https://dev.to/levinunnink/email-to-s3-3n1p)).

**Map parties to contacts with a two-stage match.** Deterministic first (look up `external_links` by `(provider, external_id)`; a hit is an UPDATE to that linked transaction), then fuzzy only when no external link exists: normalize the property address, block on street+zip, score party-name overlap with Jaro-Winkler/token-set, compare contract and close dates, and send ambiguous mid-band scores (roughly 0.6 to 0.85) to a human-review queue rather than auto-merging ([Komo.ai: entity resolution](https://komo.ai/glossary/entity-resolution); [CDQ: entity resolution](https://meta.cdq.com/Public:Entity_resolution)). Role strings must go through a translation table (vendor role string into our enum: buyer, seller, buyer_agent, listing_agent, lender, title, tc, other) while keeping the raw vendor string, so an unknown role degrades to `other` without data loss.

**(b) Build SkySlope first.** We already hold two SkySlope Access Key IDs with paired Secrets from 2020, SkySlope's Forms API exposes transactions + parties + dates + signed PDFs in one place, and DigiSign e-sign data comes free through that same API ... the shortest path to a working demo. TransactionDesk is the strong second: its key-date coverage is actually richer and it has an explicit status resource, but it has no transaction webhooks, its production URL is unpublished, and we would also need to stand up the Inkless webhook as a second moving part. Dotloop is the natural third because it is fully self-documented and would validate our vendor-independent model with the least vendor back-and-forth.

**(c) The vendor-independent data model.** Model one internal `transactions` row linked to many provider records through a thin `external_links` table carrying `(provider, external_id, external_url, last_synced, raw_payload)`, with a **unique index on `(provider, external_id)` as the dedup/idempotency gate** ([Inquir: scheduled data sync](https://inquir.org/use-cases/scheduled-data-sync)). Org-scope every table with `organization_id` per our SaaS architecture directive. Supporting tables: `contacts` (global person/company per org, with their own provider-id links to dedup people across vendors), `transaction_parties` (join of `transaction_id` + `contact_id` + normalized `role` + `provider_role_raw` + `provider`), `webhook_events` (immutable raw event log, the replay/DLQ source), and `sync_state` (per-account polling cursor). Store `raw_payload` as jsonb on both `external_links` (latest snapshot) and `webhook_events` (immutable log). This structure is what makes **signed addenda and amendments update the existing deal instead of duplicating it**: because an amendment arrives against the same vendor file/loop/transaction id, the external-id-first lookup routes it straight to the parent, where you store the addendum as a new `documents` row with a `version`/`executed_at` and bump the transaction's fields ... never letting a document event create a new transaction. Dotloop's loop-merge behavior (a 301 redirect to a surviving loop) is handled by updating the `external_id` on the existing row rather than creating a duplicate ([Dotloop Public API v2 docs](https://dotloop.github.io/public-api/)).

**(d) Realistic effort and gotchas per adapter.**

- **SkySlope adapter (build first).** Medium effort if the 2020 keys work and the Forms OAuth path is granted; higher if we must negotiate fresh partner credentials. Gotchas: refresh tokens rotate on every use, so a single shared-token refresher (one worker writing to a shared store) is needed rather than per-instance refresh, which on serverless would race and log instances out ([SkySlope Partner API docs](https://forms.skyslope.com/partner/api/docs)). Agent-level keys see only that agent's files, so brokerage-wide ingestion is really N agent connections to stagger and scope ([Drivetrain guide](https://integrations.drivetrain.ai/integration-guide/readme/others/integrating-with-skyslope)). No status/stage field and no deadline fields on the Forms File means we either parse form fields or pursue the BETA Transaction Management API. **Unknowns to resolve with SkySlope: do the 2020 keys still work and against which API; is there a transaction-created/status-changed webhook; the signing webhook payload schema; rate limits; API cost.**
- **TransactionDesk adapter (build second).** Higher effort because it is poll-only for transactions plus a second webhook integration (Inkless) for real-time execution, and the production URL is unknown until Lone Wolf provides it. Gotchas: the 10-minute auth-code expiry and unclear Bearer refresh mechanics; the `On-Behalf-Of` GUID mapping per agent; unconfirmed "modified since" filter on `GET /v2/transactions` (without it, polling is expensive); unverified whether e-signed docs auto-file into the transaction's documents list; and the open question of whether the Inkless `transactionId` matches the TransactionDesk `{id}`. **Unknowns to resolve with Lone Wolf: production base URL; rate limits; token refresh; pricing/partner terms; whether signed docs auto-file; the modified-since filter.**
- **Cross-cutting gotchas.** No sandbox is documented for SkySlope or TransactionDesk transaction APIs, so expect to develop against a real (ideally low-stakes) brokerage account with write-guards, and keep all tokens in env vars or Supabase Vault with no real client data in fixtures, per our security-first rule ([SuperGood: Dotloop API report](https://supergood.ai/docs/dotloop-api)). Partner approval and any signed API license is the single most likely thing to block the build and is outside engineering control, so start those conversations immediately ([SuperGood: Dotloop API report](https://supergood.ai/docs/dotloop-api)). MLS/brokerage data rules (MichRIC/GMAR in our market) constrain redisplay, though brokerage-owned file data (parties, dates, documents) is generally less restricted than IDX listing redistribution... confirm against our brokerage/MLS agreements.

---

## Conclusion

The integration our team wants ... write a contract once, see it everywhere, with no re-keying ... is well within reach for both platforms, and the technical design is not the hard part. The hard part is that neither vendor hands us the real-time "a contract was just executed" signal on the transaction side; SkySlope documents only a signing webhook, and TransactionDesk documents none at all, pushing that event onto the e-signature product (Inkless). This is the quiet architectural lesson: **the e-signature completion, not the transaction record, is the most reliable "it's done" trigger across this entire ecosystem**, which is why our receiver should treat every event as a nudge to go re-fetch, and why a scheduled reconciler is not a nice-to-have but the actual backbone of the sync. Build to that shape once and every future vendor, Dotloop included, plugs into the same receiver and the same `external_links` table.

The decisive near-term move is a single email or call to the SkySlope partner team with five pointed questions, because the answers (especially whether our 2020 keys still work and whether a transaction webhook exists) change the build materially and cost nothing but a few days of waiting. Starting that conversation now, in parallel with scaffolding the Supabase schema and the webhook receiver, converts the biggest uncontrollable risk ... partner-gating lead time ... into something that runs quietly in the background while the engineering proceeds. Everything flagged as uncertain in this report is a question for a vendor API team, not a gap in our plan.
