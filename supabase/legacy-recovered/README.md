# Legacy recovered migrations (reference / provenance only — DO NOT EXECUTE)

These eight `.sql` files are the **authentic SQL bodies** recovered verbatim from the
production database's `supabase_migrations.schema_migrations.statements` column
(project `bjtesdlddhxsosktzobv`), captured 2026-09-12. They are the statements that
were actually recorded for the eight pre-Phase-0 migrations.

## Why they live here and NOT in `supabase/migrations/`

**They are an incomplete, non-reproducible history.** Replaying them against a fresh
database does **not** reproduce production. Verified on a throwaway database:

1. `20260719192247_leads_rename_enable_rls_anon_insert.sql` runs
   `alter table public."Leads" rename to leads;` — but the `"Leads"` table was created
   in the **Supabase dashboard/table editor**, not by any migration. On a fresh DB this
   errors: `relation "public.Leads" does not exist`.
2. `20260816021201_create_leads_table.sql` uses `create table if not exists public.leads`
   with `id uuid` + `email not null`, but production's real `leads` is
   `id bigint generated by default as identity` + `email` nullable. In production that
   migration was a **no-op**; replaying it builds the *wrong* table.
3. That same file creates a policy `"Anon can insert leads"`, yet production's `leads`
   carries only `"Allow anonymous lead submissions"` — i.e. production was **further
   edited manually/dashboard-side** after these migrations ran.

In short: **production contained dashboard/manual schema changes that were never
captured as migrations**, so this recorded history cannot rebuild the database.

## What replaces them

The reproducible history lives in `supabase/migrations/`:

- `20260101000000_baseline_pre_phase0.sql` — a **baseline (squash)** that reproduces the
  exact net **pre-Phase-0** production schema. It is clearly a baseline, **not** a
  reconstruction labeled as an "original."
- `20260912215211_phase0_org_tenancy_foundation.sql`
- `20260912220434_phase0_secdef_hardening.sql`

`baseline → phase0_org_tenancy_foundation → phase0_secdef_hardening` reproduces current
production (verified by a catalog-level schema diff).

## Status of these files

- **Never executed as migrations.** They are retained for **audit / provenance** only.
- They remain the record of how the schema evolved historically.
- The 8 corresponding entries in the remote `schema_migrations` history are reconciled to
  the baseline via the supported `supabase migration repair` mechanism (metadata only).
